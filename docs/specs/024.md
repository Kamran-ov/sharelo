## Proposal

### 1. Compose for the server — `deploy/compose.server.yml`
Used as `docker compose -f compose.prod.yml -f deploy/compose.server.yml …` (every script and doc uses exactly this pair; `deploy/lib.sh` holds it once as `COMPOSE="docker compose -f compose.prod.yml -f deploy/compose.server.yml"`, sourced by the scripts).
- `backend`: `ports: !reset []` (Compose ≥ 2.24 `!reset` tag; removes the laptop's `8000:8000` so the laptop file stays unchanged); environment overrides `ALLOWED_HOSTS: ${SHARELO_HOST:?set SHARELO_HOST in .env}`, `CSRF_TRUSTED_ORIGINS: https://${SHARELO_HOST}`, `HTTPS: "1"` (forced, not read from `.env`: the tunnel is always https, and a server with `HTTPS=0` would boot with insecure cookies — the wrong-but-booting case). `env_file: [{path: .release.env, required: false}]` for the version line (§6).
- `cron`: same three env overrides plus `BACKUP_REMOTE: ${BACKUP_REMOTE:-}`, `RCLONE_CONFIG: /etc/sharelo/rclone.conf`; volumes `/var/backups/sharelo:/var/backups/sharelo` (dumps live on the host disk, survive container rebuilds) and `/etc/sharelo:/etc/sharelo:ro` (rclone config written by Kamran, never in git).
- `cloudflared`: `image: cloudflare/cloudflared:<pinned tag>` (multi-arch official image, tag pinned literally), `command: tunnel --no-autoupdate run`, `environment: TUNNEL_TOKEN: ${TUNNEL_TOKEN:?set TUNNEL_TOKEN in .env}`, `depends_on: [backend]`, `restart: unless-stopped`, no ports.
- **No service publishes a host port.** Trusting `X-Forwarded-Proto` is safe only because of this: the backend is reachable solely from `cloudflared` on the compose network. Stated in `docs/deploy.md` and as a comment in the file.
- The db password stays the internal `sharelo` from `compose.prod.yml` (no port anywhere; changing it would require a volume migration — out of scope, noted in docs).

### 2. Images for arm64 and amd64 — `Dockerfile` (cron stage)
- supercronic chosen by `ARG TARGETARCH` (buildx sets it): two literal sha256 ARGs (`SUPERCRONIC_SHA256_AMD64`, `SUPERCRONIC_SHA256_ARM64`) copied from the v0.2.33 release page; download `supercronic-linux-${TARGETARCH}`, `sha256sum -c` against the matching one; build fails on mismatch or an unknown arch.
- Installs `postgresql-client-17` from the PostgreSQL apt repo (Debian's own client is 15 and `pg_dump` refuses a newer server), `rclone` (Debian), `curl`. Copies `deploy/backup.sh`, `deploy/restore.sh`, `deploy/lib.sh` to `/app/deploy/`.
- The `web` and `app` stages are already arch-neutral (node/python official multi-arch images, pure-Python wheels or wheels for both arches; `psycopg[binary]` ships both).

### 3. Settings
No functional change: `SECURE_PROXY_SSL_HEADER` already exists. Added: tests that pin the behaviour through a real request (§Tests), and a comment naming why it is safe (no host port). `SHARELO_COMMIT` / `SHARELO_DEPLOYED_AT` read as optional env (empty = unknown; optional by design, the app must still boot on a laptop).

### 4. Backup and restore — `deploy/backup.sh`, `deploy/restore.sh`
`backup.sh` (POSIX `sh`, `set -eu`, no loops). Env: `DATABASE_URL` (required; empty → exit 2 with a message), `BACKUP_DIR` (default `/var/backups/sharelo`), `BACKUP_KEEP` (default 14), `BACKUP_REMOTE` (optional).
1. `pg_dump --format=custom --no-owner --file "$dir/.sharelo-<date>.dump.partial" "$DATABASE_URL"`; on failure remove the partial, exit non-zero.
2. `pg_restore --list` on the partial (proves the archive is readable, not just non-empty); then `mv` to `sharelo-YYYY-MM-DD.dump` (UTC date; a second run the same day replaces that day's file atomically).
3. Retention: delete all but the newest `BACKUP_KEEP` files matching `sharelo-????-??-??.dump` (`ls | sort -r | tail -n +15 | xargs -r rm --`; the date format makes name order = age order; other files in the dir are never touched).
4. If `BACKUP_REMOTE` is set: `rclone copy "$file" "$BACKUP_REMOTE"`; failure → exit non-zero (local file is kept). Remote retention is left to the bucket's lifecycle rule (documented for R2), not to the script.
5. Prints the file path and size. Crontab: `30 3 * * * /app/deploy/backup.sh` (03:30 container time = UTC; the Ubuntu VM default is UTC too, so "server time" and UTC agree — stated in docs). supercronic logs a non-zero exit to the container log.

`restore.sh <file>` (`set -eu`). Env `DATABASE_URL` = the target.
- Refuses (exit 3, nothing written) if the file is missing/empty or `pg_restore --list` cannot read it, and **if the target database already has any table in schema `public`** (a restore is only ever into a fresh database; it never overwrites live data).
- `pg_restore --no-owner --exit-on-error --single-transaction --dbname "$DATABASE_URL" "$file"`; prints the restored `ledger_expense` row count.
- Docs give the server procedure: stop `backend` and `cron`, `dropdb`/`createdb` inside `db`, `$COMPOSE run --rm cron /app/deploy/restore.sh /var/backups/sharelo/<file>`, start again.

### 5. Update and auto-deploy — `deploy/update.sh`, `deploy/autodeploy.sh`
**Decision (deviation from the ticket's wording, reversible; see Open question 1): auto-deploy runs on the host from a systemd timer, not inside the `cron` container.** `update.sh` rebuilds and recreates every container, including `cron`; a script running inside `cron` would be killed by its own deploy before the health check and the rollback, i.e. exactly when it is needed. It would also need the Docker socket and the repo mounted into a container (root on the host). On the host, `git` and `docker` are already there. `bootstrap.sh` installs `deploy/systemd/sharelo-autodeploy.{service,timer}` (`OnCalendar=*:0/10`, `Type=oneshot`, `TimeoutStartSec=30min` so a hung build is killed). Backups still run nightly from the `cron` service as the ticket says.

`update.sh [<commit>]` (`bash`, `set -euo pipefail`, run from the repo dir):
1. `git fetch origin "$DEPLOY_BRANCH"` (default `main`, from env or `.env`).
2. `git checkout --force -B "$DEPLOY_BRANCH" "${1:-origin/$DEPLOY_BRANCH}"` — the server never has local commits, so this is `git pull` that also works for a rollback target. `.env`, `.release.env` are gitignored and untouched.
3. `$COMPOSE build`; `$COMPOSE run --rm backend python manage.py migrate --noinput` (a failing migration stops here, before any running container is replaced); write `.release.env` (`SHARELO_COMMIT=<short sha>`, `SHARELO_DEPLOYED_AT=<UTC ISO>`); `$COMPOSE up -d`.
4. Prints `deployed <short sha> (<subject>)`. Never `down`, never `-v`, never `volume rm` (test-guarded).

`autodeploy.sh` (`bash`, `set -euo pipefail`). Env/`.env`: `AUTODEPLOY`, `DEPLOY_BRANCH`, `SHARELO_HOST`; overridable for tests: `STATE_DIR` (default `/var/lib/sharelo`), `LOG_FILE` (default `/var/log/sharelo/deploy.log`).
1. `AUTODEPLOY=0` → exit 0, nothing run (checked before the lock and before any git call).
2. Lock: `exec 9>"$STATE_DIR/autodeploy.lock"; flock -n 9 || exit 0` (held → exit immediately, logged as "skipped: another run holds the lock").
3. `git fetch origin "$DEPLOY_BRANCH"`; `new=$(git rev-parse origin/$DEPLOY_BRANCH)`, `old=$(git rev-parse HEAD)` (the running commit = the checkout, since only `update.sh` moves it). Equal → exit 0, nothing logged. `new` equals `$STATE_DIR/failed-commit` → exit 0 (a commit that already failed is not retried every 10 minutes; the next push to `main` is).
4. Backup first: `$COMPOSE exec -T cron /app/deploy/backup.sh`; failure → log "backup failed, deploy skipped", exit 1 (no deploy without a fresh backup).
5. `update.sh "$new"`; then health: `curl -fsS -o /dev/null --max-time 10 --retry 10 --retry-delay 5 --retry-all-errors --retry-max-time 60 "https://$SHARELO_HOST/api/me"` (one bounded command, not a loop).
6. Success → log `deployed <old>→<new>`, clear `failed-commit`. Failure of update or health → `update.sh "$old"`, write `new` to `failed-commit`, log `rolled back <new>→<old>: <reason>` with reason `update failed (exit N)` or `health check failed (curl exit N)`, exit 1. The database is **not** auto-restored on rollback: migrations are additive in this project and a restore would discard writes made since the backup; the pre-deploy dump is there for a manual restore (docs).

## Edge cases
- Two backups on one day (nightly + pre-deploy): same file name, the later replaces the earlier atomically via `mv`; retention counts days, not runs.
- Disk full during `pg_dump`: non-zero, partial removed, previous dumps untouched.
- `BACKUP_REMOTE` set but `/etc/sharelo/rclone.conf` missing: rclone fails → non-zero → the pre-deploy backup fails → no deploy (logged).
- Commit that fails health check: rolled back once, then not retried until `main` moves (`failed-commit`); docs say how to clear it.
- A migration in the failed commit already applied: old code runs against the newer schema; additive migrations keep it working; otherwise the docs' manual restore from the pre-deploy dump. No automatic restore (would lose writes).
- Health check against the real public hostname also tests the tunnel; a Cloudflare outage during a deploy causes a rollback of a good commit — acceptable (retried on the next push; docs explain).
- Timer firing while a manual `update.sh` runs: `update.sh` takes the same lock (`flock -n` → refuses with a message) unless it is called by `autodeploy.sh`, which passes `SHARELO_LOCK_HELD=1` because it already holds it; so the two never overlap. Test: `test_update_refuses_while_lock_is_held` ↔ the autodeploy success case.
- `.env` values with spaces/quotes: scripts read only `AUTODEPLOY`, `DEPLOY_BRANCH`, `SHARELO_HOST` with a fixed-key `grep` + `cut`, never `source .env`.

## Open questions

Every other behaviour (10-minute cadence, lock, backup → update → health → rollback, `AUTODEPLOY=0`, log path) is as the ticket says. Backups do run from the `cron` service. Reversible.
2. **Assumed:** "03:30 server time" = 03:30 UTC (container clock; Ubuntu cloud images default to UTC).
3. **Assumed:** `HTTPS` is forced to `1` by `deploy/compose.server.yml`; `HTTPS=1` in the server `.env` template is documentary only.
4. **Assumed:** the server's `.env` template is a separate `deploy/env.server.example` (the root `.env.example` keeps laptop/local values; mixing both would make `SHARELO_HOST` look required on a laptop).
5. **Assumed:** the version is an additive `version` field on `/api/me` (no new endpoint), shown on the group Settings page (the only Settings page).
6. **Assumed:** the KEY test restores into a fresh sibling database instead of dropping the pytest database (dropping it would break every later test in the session); same property.
