Ticket: `tickets/009-auth-api.md` · risk: risky (identity, sessions, access control)

## Current state
Not already done. There is no API layer at all.

## Proposal
**Dependencies and settings**
- Add `google-auth>=2.30,<3` to `requirements.txt` (the only new feature dependency; `verify_oauth2_token` needs a `google.auth.transport.requests.Request`, so `requests` is pinned alongside it — see Open questions).
- `REST_FRAMEWORK`: `DEFAULT_AUTHENTICATION_CLASSES = [SessionAuthentication]` (CSRF for anonymous POSTs is handled separately, see CSRF below), `DEFAULT_PERMISSION_CLASSES = [AllowAny]` (each view declares more), `DEFAULT_THROTTLE_RATES = {"auth": "10/min"}`, `NUM_PROXIES = 0`, `EXCEPTION_HANDLER = "accounts.api.errors.handler"`.
- `CSRF_TRUSTED_ORIGINS`: read from env (comma list, empty by default). No `django-cors-headers`: dev is single-origin through the Vite proxy. There is no proxy in `frontend/vite.config.ts` today, so this ticket adds it: `server.proxy["/api"] = { target: "http://localhost:8000", changeOrigin: false }`. With `changeOrigin: false` the `Host` header stays `localhost:5173`, equal to the browser's `Origin`, so Django's same-origin CSRF check passes with no trusted-origin entry. If someone sets `changeOrigin: true`, `Host` becomes `localhost:8000`, `Origin` no longer matches, and `CSRF_TRUSTED_ORIGINS=http://localhost:5173` is required; `.env.example` and `docs/api.md` say so. The proxied `Host: localhost:5173` must pass `ALLOWED_HOSTS` or Django raises `DisallowedHost` (400) before the CSRF origin check: `ALLOWED_HOSTS` defaults to `localhost,127.0.0.1` (host without port is matched), and `docs/api.md` says an env-driven `ALLOWED_HOSTS` must keep `localhost`. `make test-frontend` and `tsc --noEmit` must stay green.
- `AUTH_PASSWORD_VALIDATORS` set to Django's four defaults (currently unset, so "default validators apply" needs this).
- `GOOGLE_CLIENT_ID = os.environ.get("GOOGLE_CLIENT_ID", "")`; empty means Google disabled (explicitly **not** a boot failure, unlike `SECRET_KEY`: it is optional by design).
- Session cookie `HttpOnly` (default), `SameSite=Lax`; `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE` follow `not DEBUG`.

**Migration** `accounts/0004_profile_google_sub`: `google_sub = CharField(max_length=255, null=True, blank=True)` with a `UniqueConstraint` where not null. No edit of committed migrations.

**Services (logic out of views)** — `accounts/services/`
- `auth.py`: `register(email, password, display_name) -> Profile`, `authenticate_email(email, password) -> User`, `login_with_google(claims) -> Profile`. All raise `LedgerError`; `register` runs in one transaction (User + Profile).
  - Email normalisation: `email.strip().lower()`, stored as both `User.username` and `User.email`. Uniqueness check is on `username` (already lower-cased) inside the transaction; a race is caught as `IntegrityError` → `email_taken`. Validation: basic shape via Django's `validate_email`, password via `validate_password(password, user)`; failures → `invalid_email` / `weak_password` (detail lists the validator messages). `display_name` stripped, 1–100 chars, else `invalid_display_name`.
  - Google: user matched **by `google_sub` first**, else by lower-cased email, else created. When matched by email and `google_sub` is empty it is stored; when the account already has a *different* `google_sub` → `google_conflict`. Google claims with `email_verified` false → `google_invalid` (an unverified address must not take over a password account). New Google users get `set_unusable_password()`.
- `google.py`: `verify_id_token(token) -> {email, sub, name, email_verified}`; the only caller of `google.oauth2.id_token.verify_oauth2_token`. Any exception → `LedgerError("google_invalid")`. Empty `GOOGLE_CLIENT_ID` → `LedgerError("google_disabled")` (checked before the library is touched).
- `access.py`: `member_for(request, group) -> Member | None` is an ordered fallback, independent of authentication: (1) if the user is authenticated and has a profile member in `group`, that member; (2) else a member whose id is in `request.session["guest_member_ids"]` **and** belongs to `group` (a stale or foreign id never matches), so a signed-in user without a profile member in this group still resolves through their guest id; (3) else `None`. The profile member wins over a guest id in the same group. `require_member(request, group) -> Member` raises `LedgerError("not_found")` (HTTP 404, same body a missing group gets). `add_guest_member(request, member)` appends to the session list (deduplicated, `session.modified = True`) — used by 010; included here because the session shape is this ticket's contract. An authenticated user with a profile membership wins over a guest id.

**API** — `accounts/api/{views,serializers,errors,throttles}.py`, routed under `/api/` in `sharelo/urls.py`
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/google`, `GET /api/me`. Serializers only shape and validate input types; every rule is in the services.
- `/api/me` returns `{authenticated, profile: {id, display_name, email, main_group_id} | null, guest_memberships: [member_id...], google_enabled}`; anonymous → `authenticated: false, profile: null`. `google_enabled` = `bool(settings.GOOGLE_CLIENT_ID)`. `guest_memberships` is filtered to ids that still exist (no dangling ids shown).
- Login/register/google responses are the `/api/me` body. Login rotates the session key (`django.contrib.auth.login` does) and **keeps** `guest_member_ids` (Django's `login` flushes the session only when switching users; we re-read and re-set the list after login so a guest who registers keeps their guest memberships; asserted by a test).
- Logout: `django.contrib.auth.logout` flushes the session (guest ids are cleared too: acceptable, stated in the docs).
- Wrong password and unknown email both return 401 `invalid_credentials` with identical bodies (no account enumeration at login). Register necessarily reveals `email_taken` (the ticket requires it).
- Error mapping (`errors.handler`): `LedgerError` → `{code, detail}` with a code→status table: `email_taken`, `invalid_*`, `weak_password`, `google_conflict` → 400; `invalid_credentials`, `google_invalid`, `not_authenticated` → 401; `not_found` → 404; `google_disabled` → 503. DRF's own `NotAuthenticated`, `Throttled` (429, code `throttled`), `PermissionDenied` (CSRF failure → 403 code `csrf_failed`), `ParseError`/`ValidationError` (400 `invalid_request`) are mapped to the same `{code, detail}` shape. Unknown `LedgerError` codes fall to 400 (visible in the table test).
- Throttle: `AuthThrottle(SimpleRateThrottle)` (not `AnonRateThrottle`, whose `get_cache_key` returns `None` and so allows every authenticated caller), scope `auth`, key always `scope` + `get_ident(request)` whatever the authentication state, i.e. keyed by client IP (`REMOTE_ADDR`; `X-Forwarded-For` is **not** trusted — a proxy setting belongs to the release step; noted in Out of scope), applied to login, register, google. All three share one scope/bucket: 10 attempts per minute in total per IP. Throttle state in the default cache (locmem); tests clear the cache in an autouse fixture. Production multi-process: per-process counts are a known limit, recorded in the doc, shared cache arrives with hosting.
- CSRF (revised after review): DRF wraps every `APIView` in `csrf_exempt`, and `SessionAuthentication` checks the token only for an already-authenticated session user, so neither protects the anonymous POSTs. Mechanism: `accounts/api/csrf.py` defines `CsrfProtectedAPIView(APIView)` decorated with `method_decorator(csrf_protect, name="dispatch")`; login, register, google and logout derive from it. A failed check calls `settings.CSRF_FAILURE_VIEW = "accounts.api.errors.csrf_failure"`, a plain Django view returning `JsonResponse({"code": "csrf_failed", "detail": "CSRF check failed."}, status=403)`, the same `{code, detail}` shape as every other error. `GET /api/me` is `@ensure_csrf_cookie` and sets the `csrftoken` cookie the frontend echoes in `X-CSRFToken`. The handler's `PermissionDenied` mapping still covers the authenticated `SessionAuthentication` path with the same `csrf_failed` code. `APIClient(enforce_csrf_checks=True)` is used only by the CSRF pair; the default `APIClient` sets `_dont_enforce_csrf_checks`, so every other POST test runs without a token on purpose.

## Edge cases
- Register while already logged in: allowed, switches the session to the new user (documented; 010 does not depend on it).
- Same email registered via password after a Google-created account exists: `email_taken` (the user must log in with Google; no merge in this ticket). Google login onto a password account with same verified email: allowed, links `google_sub` (the ticket's rule).
- Two concurrent registrations of one email: second gets `email_taken` through the `IntegrityError` path, tested by calling the service after a pre-created user with the same username.
- Email with surrounding spaces or upper case is normalised before every lookup. `username` max length 150 is respected; a longer email → `invalid_email`.
- Guest ids in the session pointing to deleted members vanish from `/api/me`.
- Empty/absent `GOOGLE_CLIENT_ID` never reaches `google-auth` (a misconfigured prod cannot accept any token by accident).

## Build notes (from review)
- `csrf_protect` on `dispatch` runs before DRF authentication: an unauthenticated tokenless POST goes through `CSRF_FAILURE_VIEW`, an authenticated one in 010 through `SessionAuthentication` → `PermissionDenied` → handler; both give the identical `{code: "csrf_failed", detail}` body and `test_error_bodies_always_have_code_and_detail` samples both paths.
- In `register`, the `IntegrityError` → `email_taken` catch sits outside the `atomic()` block (or in its own savepoint) and matches the `auth_user` username constraint only, not any `IntegrityError`.
