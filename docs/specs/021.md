## Proposal

### Models (app `importers`, one new migration `importers/0002_shoprule_bankrow_decision.py`)
`ShopRule`:
| field | type |
|---|---|
| `group` | FK `ledger.Group`, PROTECT, related_name `shop_rules` |
| `match_text` | CharField(200), stored stripped with spaces collapsed |
| `category` | FK `ledger.Category`, PROTECT |
| `preset` | CharField(20), `ledger.SplitType` choices (service form: `equal`, `personal`, `full_for_other`, `percentage`, `exact`, `shares`) |
| `params` | JSONField default `{}` |
| `created_by` | FK `ledger.Member`, PROTECT |
| `created_at` / `updated_at` | auto |
| `last_used_at` | DateTimeField null |
| `deleted_at` | DateTimeField null (FACTS: soft delete only; default manager hides deleted, `all_objects` shows) |

Constraints: `UniqueConstraint(Lower("match_text"), "group", condition=Q(deleted_at__isnull=True),
name="uniq_shoprule_group_text")` (one live rule per text per group, so "remember" can
create-or-update); `CheckConstraint(match_text != "")`.

`PendingBankRow` gains (additive, nullable/defaulted, no data migration):
- `expense` FK `ledger.Expense`, null, PROTECT, related_name `+` — the expense this row made;
  kept after an Undo (the expense is then soft-deleted) so a re-decision revives it (below).
- `split_preset` CharField(20, blank) and `split_params` JSONField default `{}` — the Shared
  split **as decided on this row** (service preset + its params; `personal` rows store
  `personal`/`{}`). The "last choice" suggestion reads preset **and** params from these two
  columns only, never one from the expense and one from the row (plan review 1: an expense
  edited later on the expense sheet would otherwise pair `percentage` with `{}`).

### Services (business logic in `services`-style modules of the app, as in 020)
`backend/importers/banks/shop_rules.py`:
- `match_key(text) -> str`: `collapse_spaces(text).casefold()`.
- `row_text(row) -> str`: `row.merchant or row.description` (collapsed) — the text "remember"
  stores and history compares.
- `find_rule(rules, row) -> ShopRule | None`: rules whose `match_key(match_text)` is contained
  in `match_key(merchant)` **or** `match_key(description)`; the longest `match_text` wins; tie →
  lowest id (deterministic). Pure over a list, so a page of rows costs one rule query.
- `save_rule(group, member, *, match_text, category, preset, params, rule=None)`: validates
  (empty text → `invalid_request`; category must be a leaf — no children — else
  `invalid_category`; dry-run `split_for_preset(preset, 100, group members, member.id, params)`
  like `CategoryDefaultsView.put`), then creates or updates. Create-or-update by
  `Lower(match_text)` among live rules of the group (`remember` path); explicit `rule` for the
  Settings edit path. A text collision on edit → `LedgerError("duplicate_rule")`.
- `delete_rule(rule)`: sets `deleted_at` (idempotent).

`backend/importers/banks/review.py`:
- `@dataclass Suggestion(category: Category, decision: "shared"|"personal", preset: str,
  params: dict, basis: "rule"|"history"|"default", rule_id: int | None)`.
  `preset`/`params` are always the split the **Shared** button will use (never `personal`);
  `decision` says which button is highlighted.
- `suggest_many(group, rows) -> dict[row_id, Suggestion]` (and `suggest(row)` = one-row
  wrapper, the ticket's name). Order:
  1. **Rule** (`find_rule`): category = rule's; preset `personal` → decision `personal`;
     otherwise decision `shared`, preset/params = rule's.
  2. **History**: the group's most recent row (by its expense's `updated_at`, then row id) with status
     `shared`/`personal`, a live expense, and the same `match_key(row_text)` → category = that
     **row's** expense category (a later category correction is the better guess and cannot make
     a split invalid), decision = the row's status, preset/params = the row's
     `split_preset`/`split_params` (one record, one consistent pair). One query for all rows of
     the page.
  3. **Default**: Uncategorized › General, decision `shared`, preset/params =
     `default_split_for(group, General)`.
  Whenever the chosen preset is `personal`, the Shared preset is `shared_split_for(group,
  category)`.
  **Validity guard** (rule and history branches): the pair is dry-run with
  `split_for_preset(preset, 100, group members, uploader, params)`; if it raises (e.g. a rule's
  `percentage` keyed on a member set that changed), the suggestion keeps its category but the
  split becomes `shared_split_for(group, category)`. So a suggestion is never a pair the tap
  would refuse.
- `shared_split_for(group, category) -> (preset, params)`: `default_split_for`, with `equal`
  when that default is `personal`. **The one place** the "split for a category" rule lives;
  `shared_splits_for_group(group) -> dict[category_id, (preset, params)]` is the same rule for
  every leaf category in one `CategoryDefault` query (used by the API, below).
- `resolve_row(row, member, decision, *, category=None, preset=None, params=None, payer=None,
  remember=False) -> Resolved(row, expense | None, rule | None)`:
  1. `row.uploaded_by_id != member.id` or another group → `LedgerError("not_found")` (statement
     is the uploader's, as in 020).
  2. `decision` ∉ {`shared`, `personal`, `skip`} → `invalid_request`. `remember` with `skip` →
     `LedgerError("remember_needs_category")` (a rule has no "skip" outcome).
  3. Fill from `suggest(row)`: category omitted → suggestion's; for `shared`, preset omitted →
     suggestion's preset if the category is the suggested one, else `shared_split_for(group,
     category)` (service-level default for non-UI callers; the UI always sends the preset and
     params it displays, see API/Frontend); `shared` with preset `personal` →
     `LedgerError("shared_needs_split")`. `personal` → preset `personal`, params `{}`. `payer`
     defaults to `row.uploaded_by` (the statement's owner; ticket: no payer detection).
  4. One `transaction.atomic()` (HARD RULE 2): `select_for_update` the row; status ≠ `pending`
     → `LedgerError("row_already_resolved")`. Then:
     - `skip` → status `skipped`; nothing else.
     - `shared`/`personal`, no `row.expense` → `create_expense_from_preset(group, preset=…,
       payer_id=payer.id, params=…, description=row_text(row), date=row.date,
       category=…, currency=group.currency, source=row.source, external_id=row.external_id,
       import_batch=row.import_batch, **amount)` where `amount` is `amount_cents=row.amount_cents`
       when `row.currency == group.currency`, else `original_amount_cents=row.amount_cents,
       original_currency=row.currency` (conversion at the row's date, `no_rate` propagates and
       the row stays pending).
     - `row.expense` set (a previous decision was undone) →
       `revive_expense_from_preset(row.expense, …same values…)` (below).
     - `row.status` = decision, `row.expense` = the expense, `row.split_preset`/`split_params`
       = the preset/params actually used
       (no `resolved_at` column: history orders by the expense's `updated_at`, then row id).
     - `remember` → `save_rule(group, member, match_text=row_text(row), category, preset, params)`
       (create or update). Else if a rule matched (`basis == "rule"`) → its `last_used_at = now`.
  `duplicate_external_id` (the same bank row already shared in **another** group — 020 Out of
  scope) propagates as 400 with that code; the row stays pending and can be skipped.
- `undo_row(row, member) -> PendingBankRow`: same access rule; one transaction,
  `select_for_update`; `pending` → `LedgerError("row_not_resolved")`; `shared`/`personal` →
  `delete_expense(row.expense)` (soft); status back to `pending`. A rule created by "remember"
  stays (Open question 2).

`backend/ledger/services/expenses.py` — one addition, needed because a soft-deleted expense
keeps its `(source, external_id)`:
- `revive_expense_from_preset(expense, *, preset, payer_id, params, description, date,
  category, amount_cents=None, original_amount_cents=None, original_currency=None)`: refuses a
  live expense (`LedgerError("expense_not_deleted")`); in one transaction clears `deleted_at`
  and calls `update_expense` with payers/splits computed exactly as
  `create_expense_from_preset` does. The amount/split computation is factored into one private
  helper used by both, so the two paths cannot drift. Same id, same `external_id`.

### API (`importers/api/`, all views derive from `GroupScopedView`)
- `GET groups/{id}/bank-rows/` → my `pending` rows (all batches, `uploaded_by = me`), ordered
  `date, id`, each `{id, date, amount_cents, currency, description, merchant, source, status,
  suggestion: {category, category_name, decision, preset, params, basis, rule}}`, wrapped as
  `{rows: [...], category_splits: {<category_id>: {preset, params}}}` where `category_splits` is
  `shared_splits_for_group` for every leaf category (plan review 2). Re-opening the page shows
  what is left to review.
- `POST groups/{id}/bank-rows/{rid}/resolve` body `{decision, category?, preset?, params?,
  remember?}` (the page always sends `category`, `preset`, `params` for `shared` — exactly what
  it displays; the service fills omitted values only for other callers) → 200 `{row, expense, rule}` (ids; `null` when none). Presets go through
  `to_service_preset` (so `half` works as on the expense sheet). Errors 400:
  `row_already_resolved`, `shared_needs_split`, `remember_needs_category`, `no_rate`,
  `duplicate_external_id`, `invalid_params`; 404 another uploader's / group's row.
- `POST groups/{id}/bank-rows/{rid}/undo` → 200 `{row}`; 400 `row_not_resolved`.
- `GET groups/{id}/shop-rules/` → live rules `{id, match_text, category, category_name,
  preset, params, created_by, last_used_at}` ordered by `match_text`; `POST` (create, 201),
  `PATCH groups/{id}/shop-rules/{rid}/` (edit), `DELETE` (soft, 204). Any member of the group
  may manage its rules (rules are group data, not statement data).
- Upload response (`POST bank-imports/`) is unchanged; the review page re-reads
  `GET bank-rows/` after an upload.
- `test_api_access.py` route table gains the five routes; `make schema` regenerates
  `frontend/src/api/schema.json`.

### Frontend (no business logic: suggestion and split come from the server)
- `pages/Expenses.tsx`: an "Import bank file" link → `/g/:id/bank-import`, with the count of my
  pending rows when > 0.
- `pages/BankImport.tsx` (new route): file input (`.csv`) → `POST bank-imports/` → shows the
  batch counts line ("12 new, 3 already imported, 4 not money out") → review list from
  `GET bank-rows/`. Each row: date, merchant/description, amount (`lib/money.ts`), category
  chip (tap → `<select>` of leaf categories, grouped by parent, from `GET categories/`), the
  Shared split label, read-only. **What is displayed is what is sent** (plan review 2): the row
  holds one `(category, preset, params)` triple; it starts as the suggestion's; changing the
  chip replaces preset/params with `category_splits[new category]` from the same response (no
  split rule in TS, only a lookup); the label is `splitLabel(preset, params)` of that triple and
  the Shared tap sends that same triple. Three big
  buttons Shared / Personal / Skip (suggested one outlined), "remember for this shop" toggle
  (disabled for Skip). A tap sends `resolve`; the row turns into a one-line result
  ("Shared · Groceries · 50/50") with **Undo** (sends `undo`, row returns pending) for as long
  as the page is open; rows resolved in an earlier visit are not listed. Errors show inline on
  the row (`detail` text), the row stays pending.
- `pages/ShopRules.tsx`, rendered in `Settings.tsx` under "Shop rules": list (text → category ·
  split label, last used date), edit sheet (text, category select, the same `Who` choices as
  default splits), delete with confirm.
- `lib/bankImport.ts`: `rowChoice(suggestion, categorySplits, chosenCategory?)` → the triple,
  `splitLabel(preset, params, me, members)`, `resolveBody(decision, triple, remember)` and
  `resultLine(...)` (pure, vitest).

## Open questions (all assumed, reversible)
1. **Text a "remember" rule stores** — assumed the row's merchant, else its full description
   (collapsed spaces), e.g. Revolut "Esselunga". Long Wise descriptions make a narrow rule; the
   user shortens it in Settings. Alternative: strip trailing digits/cities heuristically
   (guessing; not done).
2. **Undo of a remembered choice** — assumed Undo reverts the row and its expense only; the
   rule stays (visible and deletable in Settings).
3. **Split in the review list** — assumed only the category is editable there; Shared uses the
   suggested split. Keeps "one tap"; a different split is an edit of the created expense.
4. **Payer** — assumed the uploader (whose statement it is). The service takes `payer` as the
   ticket names it; the API does not expose it.
5. **Rule visibility** — assumed group-wide (any member sees and edits shop rules), while bank
   rows stay uploader-only (020).
6. **Error code status** — the new refusals are 400 like other domain errors; no change to the
   handler's status map.
