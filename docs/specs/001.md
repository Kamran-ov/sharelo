## Proposal
**Apps.** `backend/accounts/` holds only the stub `Profile` (id, `email`; 1:1 User comes in 006). `backend/ledger/`
holds everything else. Both added to `INSTALLED_APPS`.

**Models (`ledger/models.py`)**, money as `IntegerField` cents, no Decimal except `rate_used`:
- `Group`: `name`, `currency` (CharField 3), `share_token` (unique, `secrets.token_urlsafe(16)` default), `created_at`.
- `Member`: `group` FK, `display_name`, `profile` nullable FK `accounts.Profile` (`SET_NULL`);
  `UniqueConstraint(group, display_name)`.
- `Category`: `name`, `parent` nullable self-FK (`PROTECT`), `is_default`. Depth ≤ 2 enforced in `save()`
  (guard raises `LedgerError(category_depth)`; also `clean()`). Unique (parent, name) with `nulls_distinct=False` (Django 5 / Postgres 15+), so two root categories of the same name are rejected too (a plain unique would let both through, NULLs being distinct).
- `ImportBatch`, `RecurringRule` (stub: id + group FK only, so 007 can fill it in), `Expense`, `ExpensePayer`,
  `ExpenseSplit`, `Settlement` exactly as in the ticket. DB-level `CheckConstraint`s: `amount_cents > 0`
  (expense, settlement), `paid_cents >= 0`, `owed_cents >= 0`, settlement `from_member != to_member`.
  `UniqueConstraint(source, external_id, condition=Q(external_id__isnull=False))` on Expense (and Settlement,
  same rule for re-runnable imports). Choices use the exact enum strings from CLAUDE.md.
- Soft delete: `Expense.objects` = manager filtering `deleted_at__isnull=True`; `Expense.all_objects` = plain manager.
  (`Meta.base_manager_name = "all_objects"` so FK traversal and admin are not silently filtered.)

**Seed migration** `ledger/migrations/0002_seed_categories.py` (data migration, new file, never edited later):
the Splitwise tree from the ticket verbatim, `is_default=True`, idempotent via `get_or_create`.

**Service `ledger/services/expenses.py`** plus `ledger/errors.py` (`LedgerError(code, message)`, `code` a str attribute):
- `create_expense(group, *, description, amount_cents, currency, date, category, payers, splits, split_type,
  source="manual", external_id=None, original_amount_cents=None, original_currency=None, rate_used=None,
  import_batch=None, recurring_rule=None, notes="")`.
  Everything runs inside `transaction.atomic()`; validation happens before the first write, and the unique-constraint
  `IntegrityError` is translated to `LedgerError(duplicate_external_id)` **only when the violated constraint is the named
  `uniq_expense_source_external_id`** (read via `exc.__cause__.diag.constraint_name` on psycopg); every other `IntegrityError`
  (CHECK, FK, other unique) is re-raised untouched, so a CHECK violation never surfaces as a duplicate. The unique constraint
  is named in `Meta.constraints` (Settlement: `uniq_settlement_source_external_id`). The translation runs inside a savepoint so the outer transaction stays usable.
- `update_expense(expense, **same)`: replaces payers/splits wholesale in one transaction, same validation.
- `delete_expense(expense)`: sets `deleted_at`, nothing else; a second call is a no-op that keeps the original `deleted_at` (the real deletion time is not overwritten; asserted in the soft-delete test).
- Shared validator `_validate(group, amount, currency, payers, splits)`; error codes (distinct):
  `amount_not_positive`, `invalid_currency`, `currency_mismatch` (expense currency ≠ group currency, per FACTS),
  `payers_sum_mismatch`, `splits_sum_mismatch`, `member_not_in_group`, `empty_payers`, `empty_splits`,
  `negative_share`, `invalid_split_type`, `invalid_source`, `duplicate_external_id`, `category_depth`.
- Same-currency defaults: when `original_*` are omitted the service stores `original_amount_cents = amount_cents`,
  `original_currency = currency`, `rate_used = Decimal(1)`. If any of the three `original_*`/`rate_used` is given, all three must be (`incomplete_original`).
  Conversion itself is 004; here the values are stored as given.
- Zero-valued entries are allowed (a member paying 0 or owing 0 is legitimate, e.g. `personal` for a 3-member group); negatives are not.

## Tests
`backend/tests/test_ledger_expenses.py`, `test_ledger_models.py`, `test_ledger_categories.py`. Named for properties.
Every refusal paired with a legitimate success.
- `test_payers_sum_to_total` (fail: 1 cent short → `payers_sum_mismatch`; pass: exact, incl. two payers 600+400=1000).
- `test_splits_sum_to_total` (fail: 1 cent over → `splits_sum_mismatch`; pass: 334/333/333 on 1000).
- `test_members_belong_to_group` (fail: payer from other group, and split member from other group — two cases; pass: own members).
- `test_amount_must_be_positive` (0 and −1 fail; 1 passes), `test_currency_must_be_valid_three_letter_code` ("EU", "eur", "EU1"
  fail; "EUR" passes), `test_expense_currency_matches_group_currency` (fail USD in EUR group; pass with `original_currency=USD`, `rate_used`).
- `test_failed_split_leaves_no_rows` **(KEY, atomicity)**: a splits dict whose second row is invalid at the DB level
  (member in group but `owed_cents` violates the check constraint, validator bypassed by patching the validator to a no-op)
  → the raise is the raw `IntegrityError` (asserted as such, **not** a `LedgerError`, which also guards the constraint-specific translation),
  and afterwards `Expense`, `ExpensePayer`, `ExpenseSplit` counts are all 0. Passing twin: valid call leaves 1 / n / n rows.
  Marked `@pytest.mark.django_db(transaction=True, serialized_rollback=True)`, as is `test_update_replaces_payers_and_splits_atomically`
  (same shape). Why: `transaction=True` because under the default mark the test body sits in an enclosing transaction, so with the service's atomic
  removed the `IntegrityError` aborts it and the next count query raises `InternalError: current transaction is aborted`, i.e. red on an error,
  not on the `== 0` property; with a real transaction the leftover rows are observable. `serialized_rollback=True` because a transactional test
  flushes every table at teardown, including the 50 seeded categories, which would silently break later tests that rely on the seed;
  the seed is restored from the serialized snapshot.
- `test_delete_is_soft_and_hidden_from_default_manager` (default manager 0, `all_objects` 1, `deleted_at` set; a live expense still visible).
- `test_duplicate_source_external_id_rejected` (same pair → `duplicate_external_id`, and no extra rows remain; different
  external_id OK; same external_id with different source OK) and `test_null_external_id_is_not_unique` (two manual expenses both succeed).
- `test_update_replaces_payers_and_splits_atomically` (valid update changes rows; invalid update leaves old rows intact).
- `test_category_depth_max_two` (grandchild rejected; child accepted; re-parenting a parent that has children under a
  child is rejected too), `test_seed_tree_has_parents_with_children` (the 7 parent names exactly; each ≥ 1 child;
  total children = 5+4+9+8+9+7+1 = 43).
- `test_db_constraints_hold_without_service` (raw ORM insert of a negative `paid_cents`, a zero-amount expense, or a self-settlement
  raises `IntegrityError`: the guard does not live only in the service).
- `test_model_defaults` : `share_token` unique & URL-safe, `Member` (group, display_name) unique.

**KEY test:** `test_failed_split_leaves_no_rows`. Proof: remove `transaction.atomic()` from `create_expense`; the test must fail
on the leftover-row count assertion, not on an earlier guard. The proof removes **every** atomic wrapper around the writes, including the savepoint used for the `IntegrityError` translation
(an inner savepoint would otherwise keep the writes atomic and leave the "red" run green). Because validation runs first, the proof
temporarily no-ops the validator (the test does so itself) so the failure reaches the property. Restored and shown green.
Second proof for the money guard: comment out the payers-sum check → `test_payers_sum_to_total` red on the missing raise.

## Edge cases
- 1000 split three ways 334/333/333 sums to total (accepted); 333/333/333 is rejected (`splits_sum_mismatch`, 1 cent missing).
- Payer who is also in the splits, payer outside the splits (valid), payers list with a 0 entry (valid), duplicate member
  id can't occur (dict keys) — but the DB unique (expense, member) is still tested via raw insert.
- `amount_cents = 2_147_483_647` is the `IntegerField` max (≈ €21.4M); accepted as ample for household money, noted in Open questions.
- Soft-deleted expense keeps its `(source, external_id)` so a re-import cannot recreate it (unique constraint is not filtered by `deleted_at`).
  This is deliberate: it is what keeps imports re-runnable.
- Deleting a `Member`/`Category` referenced by an expense is blocked (`PROTECT`); money rows are never cascade-deleted.
- Category with `parent` pointing to itself or forming a cycle is rejected by the depth guard. The guard terminates: it checks `parent_id == self.pk` first, then walks at most 3 steps (never a bare `while parent:`), so a cycle cannot loop forever.

## Open questions (all decided in plan review of head 2a9eeed: accepted)
1. **Category depth guard in `save()`**: CLAUDE.md rule 8 says no business logic in `save()`; the ticket requires depth enforced "at the model level" and a CHECK constraint cannot span rows. Assumed: a structural-invariant guard in `save()`/`clean()` is acceptable. Reversible.
2. **`IntegerField` vs `BigIntegerField`**: following the ticket (`IntegerField`, max ≈ €21.4M). Switching later is a migration. Assumed fine.
3. **`Expense.currency == group.currency` enforced in the service** (`currency_mismatch`), per the FACTS section, though the ticket's Acceptance lists only the 3-letter check. Assumed in scope.
4. **Unique (source, external_id) also on `Settlement`**, mirroring Expense, so settlement imports are re-runnable. Assumed.
5. **`RecurringRule` stub** (id + group) is created now because `Expense.recurring_rule` needs a target; 007 extends it.
