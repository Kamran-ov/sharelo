### `common.py` (pure, no DB)
- `@dataclass(frozen=True) BankRow(date: date, amount_cents: int, currency: str,
  description: str, merchant: str, external_id: str, raw: dict[str, str])`.
  `amount_cents` is always **positive money out** (the parsers only emit money out).
- `parse_cents(text: str) -> int`: strip spaces; regex `^-?\d+(\.\d{1,2})?$`; integer
  arithmetic on the two string halves (`"-12.5"` → −1250, `"0.10"` → 10, `"1000"` → 100000).
  Anything else (`"1,234.56"`, `"12.345"`, `"1e3"`, `""`, `"abc"`) raises
  `ValueError` inside the parser, which collects it as a bad row (below). No `float(`, no
  `Decimal`, no `round(`.
- `read_csv(data: bytes) -> tuple[list[str], list[dict[str, str]]]`: decode `utf-8-sig`
  (Revolut/Wise exports may carry a BOM); a decode error →
  `LedgerError("unknown_bank_format", "file is not UTF-8 text")`. `csv.DictReader`; header
  names stripped; fully blank lines dropped. Each dict keeps its 1-based file line number for
  error messages.
- `detect(header) -> "revolut" | "wise"`: the bank whose required column set is a subset of the
  header. Required sets:
  - Revolut: `Type, Product, Started Date, Completed Date, Description, Amount, Fee, Currency,
    State, Balance`
  - Wise: `TransferWise ID, Date, Amount, Currency, Description, Merchant`
  Neither matches → `LedgerError("unknown_bank_format", "revolut missing: <cols>; wise missing:
  <cols>")`, both lists in the ticket's column order, so the user sees what the file lacks for
  either bank. An empty file (no header) gives the same error with every column listed.
  Columns are read by name only; extra columns and any order are accepted.
- Bad rows: each parser checks every row before returning; any rows it cannot read (bad amount,
  bad date, missing value in a required column of a kept row) are collected as
  `line <n>: <column> <value>` and raised together as
  `LedgerError("bad_bank_row", "line 7: Amount '12,50'; line 9: Date '31/02/2026'")` — nothing
  is staged from a file with any bad row (same "list every error, write nothing" rule as 019).

### `revolut.py`
Per row, in this order:
1. `State != "COMPLETED"` → ignored (covers `REVERTED`, `DECLINED`, `PENDING`, `FAILED`).
2. `amount = parse_cents(Amount)`, `fee = parse_cents(Fee or "0")`.
   Money out iff `amount <= 0` and `out = fee - amount > 0`; otherwise ignored (top-ups,
   refunds, incoming transfers). So a −12.50 card payment with a 0.30 fee stages 1280.
3. `date` = date part of `Completed Date` (`YYYY-MM-DD HH:MM:SS` or `YYYY-MM-DD`), as given
   (FACTS: the day is the date given).
4. `merchant = ""`, `description = Description` (Revolut's CSV has no separate merchant
   column; the description *is* the shop name for card payments — 021 matches on either).
5. `external_id = "rv:" + sha256("\x1f".join([completed, str(amount), currency,
   description, str(balance)]).encode()).hexdigest()` over **parsed, canonical values only**
   (never raw text), so incidental formatting differences between two exports of the same row
   give the same id:
   - `completed`: `Completed Date` parsed as `YYYY-MM-DD HH:MM:SS`, `YYYY-MM-DD HH:MM` or
     `YYYY-MM-DD`, written back as `YYYY-MM-DDTHH:MM:SS`; missing seconds → `:00`; an export
     with no time part at all → `T00:00:00`. (So a dated-only export and a timed export of the
     same row would differ unless the row is at midnight; Revolut's export carries seconds,
     and the balance still separates same-day rows.) Anything else is a bad row.
   - `amount`, `balance`: integer cents from `parse_cents` (`-12.5` ≡ `-12.50`, `100` ≡
     `100.00`). A completed row with an empty `Balance` is a bad row (the id would not be stable).
   - `currency`: stripped, upper-cased.
   - `description`: stripped, internal whitespace runs collapsed to one space (`" Cafe  Roma "`
     ≡ `"Cafe Roma"`). Case is kept (a merchant's case is not incidental formatting).
   The running balance is what tells apart two identical coffees in the same second.
   **The recipe is frozen**: changing it re-stages every Revolut row ever imported. It is
   written down in `docs/adr/002-bank-row-ids.md` (with the Wise rule) and the function
   carries a comment pointing there.
6. `raw` = the row dict as read (strings only).

### `wise.py`
1. `amount = parse_cents(Amount)`; money out iff `amount < 0`, `out = -amount`; else ignored.
   No fee arithmetic: Wise's `Amount` is already the balance movement (fees included); the
   ticket asks for fee handling only on Revolut.
2. `date` from `Date`: `DD-MM-YYYY` (Wise's statement format) or `YYYY-MM-DD`; anything else is
   a bad row.
3. `merchant = Merchant`, `description = Description`.
4. `external_id = "wise:" + TransferWise ID` (empty ID on a kept row → bad row).

### `staging.py`
`stage_bank_file(group, member, file) -> StageResult(batch, ignored)`:
1. `member.group_id != group.id` → `LedgerError("member_not_in_group")`.
2. `file.size` > 2 MiB → `LedgerError("file_too_large")` **before** `file.read()`, so an
   oversized upload is never read into memory (a month of either bank is a few dozen KB).
   Then `data = file.read()`.
3. `read_csv` → `detect` → that bank's `parse` → `rows`, `ignored = rows read − rows emitted`.
   Every error happens here, before any write.
4. One `transaction.atomic()`:
   `batch = ImportBatch.objects.create(group, source=<bank>, label=file.name[:200])`;
   `PendingBankRow.objects.bulk_create([...], ignore_conflicts=True)` (Postgres
   `ON CONFLICT DO NOTHING`); `created = batch.bank_rows.count()`;
   `rows_seen = len(rows)` (money-out completed rows only), `rows_created = created`,
   `rows_skipped = rows_seen - created`, `finished_at = now()`.
   **The unique constraint is the only duplicate guard** (FACTS: `(source, external_id)` is the
   only guard for imports): no pre-query, so a concurrent upload of the same file cannot slip
   past it, duplicates *within one file* also collapse, and removing the constraint doubles the
   rows (KEY).
5. `dry_run=True` stops after step 3 plus one read-only lookup
   (`PendingBankRow.objects.filter(group, source, external_id__in=ids)`, ids de-duplicated
   within the file): no batch, no rows, nothing written. It returns a `DryRun(source,
   rows_seen, ignored, would_create, would_skip, cents_by_currency, type_counts)`;
   `type_counts` is Revolut `Type` / Wise id prefix (`CARD`, `TRANSFER`, `CONVERSION`…) of the
   kept rows, so the EXCHANGE/CONVERSION rows (Open question 1) are visible before staging.
   The lookup is read-only reporting; the real path still relies only on the constraint.
6. Rows ignored by the bank rule (declined, top-up, money in) are not stored and not counted in
   the batch; the POST response reports them as `ignored` so a file of only top-ups doesn't
   read as "nothing happened".

### API (`importers/api/`, included from `sharelo/urls.py` under `api/`)
Both views derive from `GroupScopedView`; serializers with `extend_schema` so the committed
schema stays warning-free.
- `POST groups/{id}/bank-imports/` — `MultiPartParser`, field `file` (missing → 400
  `invalid_request`). → **201** `{batch: {id, source, label, rows_seen, rows_created,
  rows_skipped, started_at, finished_at}, ignored, rows: [...]}` where `rows` are this batch's
  created rows (`id, date, amount_cents, currency, description, merchant, external_id,
  status`; `raw` is not sent). Errors: 400 `unknown_bank_format` (detail names the missing
  columns), 400 `bad_bank_row`, 400 `file_too_large`.
- `GET groups/{id}/bank-imports/{batch}/` → 200 with the same shape minus `ignored`. 404
  `not_found` when the batch belongs to another group, is not a bank batch (e.g. Splitwise), or
  **holds rows uploaded by someone else** — a personal bank statement is visible to its
  uploader only (Open question 2). The uploader is read from the batch's rows (every row of a
  batch has the same `uploaded_by`); a batch with no rows (all duplicates or all ignored)
  carries no bank data, so any member gets its counts and an empty `rows`. This avoids a
  `ledger` migration for an `ImportBatch.uploaded_by` column.
- Management command `stage_bank_file --group <id> --member <id> [--dry-run] FILE`
  (argument parsing and printing only; calls `stage_bank_file`). Dry run prints:
  `<bank>  seen <n>  ignored <n>  would create <n>  would skip <n>`, one line per currency
  `  EUR  total 1234.56  rows <n>` (cents formatted with integer `divmod`, no `/ 100`), and the
  type counts. Real run prints the batch counts. Errors → message + exit 1. This is how the
  first real export is checked before anything is staged (no upload UI until 021).
- `docs/api.md` gains both endpoints; `make schema` regenerates `schema.json`.

## Edge cases
- Revolut exports by date range overlap at the edges by design: the overlap is skipped by id.
- Two identical purchases in the same second: different running balance → different id → both
  staged. Two genuinely identical rows including balance cannot exist in one account.
- Revolut multi-currency pockets: the balance is per pocket and the currency is in the hash, so
  a EUR and a USD payment never collide.
- A row edited by the bank between two exports (e.g. description changes from pending text to
  the final merchant) gets a new hash and is staged again; 021's review shows both, the user
  skips one. Only completed rows are read, which keeps this rare. (Not fixable without a bank id.)
- Concurrent upload of the same file: both inserts use `ON CONFLICT DO NOTHING`; each batch
  counts what it actually created; no error, no double.
- A file with only ignored rows: batch 0/0/0, response `ignored = n`.
- BOM at file start, CRLF line ends, blank trailing lines: accepted.

## Production checks
Kamran checks one real export of each bank after merge (ticket note); header names come from
the banks' current exports and may need a follow-up ticket if they differ. Staged rows are
never deleted and a re-upload of a fixed parse is skipped by id, so **nothing real is staged
before step 0 matches**. Expected numbers:
0. Dry run each real file first (`manage.py stage_bank_file --group <id> --member <id>
   --dry-run FILE`), nothing written:
   - Revolut: per-currency total == spreadsheet sum of `Fee − Amount` over `COMPLETED` rows
     with `Amount ≤ 0` and `Fee − Amount > 0`; `rows_seen` == that row count;
     `ignored` == data rows − `rows_seen`.
   - Wise: per-currency total == spreadsheet sum of `−Amount` over rows with negative `Amount`.
     **Check that Wise `Amount` already includes fees**: pick one card payment with a non-zero
     `Total fees` and confirm the account balance moved by `Amount` (Running Balance before −
     after == −Amount). If it doesn't, stop: the parser needs `Total fees` added (follow-up),
     and nothing has been staged.
   - Report the `EXCHANGE` (Revolut) / `CONVERSION` (Wise) counts from the type line
     (Open question 1).
   Only when every number matches, do the real upload.
1. Upload a real Revolut month: `rows_seen` = number of `COMPLETED` rows with negative Amount
   (or Fee-only) in the file (count them in a spreadsheet); `rows_created == rows_seen`;
   `ignored` = data rows − `rows_seen`.
2. Upload the same file again: `rows_created == 0`, `rows_skipped == rows_seen`.
3. Upload the next month's export: `rows_skipped` = number of overlapping rows (same completed
   timestamp, amount and balance), the rest created.
4. Same three checks for Wise, counting rows with negative `Amount`.
5. If either file gives `unknown_bank_format`, the detail lists the columns to add to the
   parser; that's the follow-up ticket.

## Open questions
All four accepted in plan review round 1.
1. **Revolut `EXCHANGE` / transfers between own pockets, Wise `CONVERSION` rows** — assumed:
   kept like any other money out (ticket says "only money out", nothing about type); 021's
   review list lets the user Skip them. Alternative: drop `Type = EXCHANGE` (Revolut) and
   `CONVERSION-` ids (Wise) at parse time. Reversible (no rows become expenses here).
2. **Who sees a staged batch** — assumed: only the uploader (other members get 404), because a
   statement is personal. Reversible.
3. **Rows with a bad amount/date** — assumed: the whole file is refused with every bad line
   listed (as in 019), rather than staging the readable rows. Reversible.
4. **Package path** — assumed `backend/importers/banks/` (CLAUDE.md) instead of the ticket's
   `imports/banks/`.
