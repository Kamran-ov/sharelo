# Plan 003 — Balances, settlements and debt simplification

Ticket: `tickets/003-balances.md` · risk: risky (money, balances)

## Current state
- `backend/ledger/services/` has `expenses.py` and `splits.py`; there is no `balances.py`.
- `Settlement` already exists in `ledger/models.py` with `twin` nullable, `amount_cents > 0` and `from_member != to_member` CHECKs.
- The invariant `Expense.currency == group.currency` is already enforced in `expenses._validate` (`currency_mismatch`), so no new
  invariant check is needed here.
- `Expense.objects` hides soft-deleted rows; `ExpensePayer` / `ExpenseSplit` have no `deleted_at`, so they are filtered through
  `expense__deleted_at__isnull=True`. No settlement service exists. The work is not already done.

## Proposal
**`ledger/services/balances.py`** — read-only aggregation in SQL (`Sum` grouped by member), integers only, nothing stored.
- `net_balances(group) -> dict[int, int]`: every member of the group appears (0 if no activity). net = Σ paid − Σ owed over
  non-deleted expenses, + Σ settlements sent − Σ settlements received. Asserts `sum(values) == 0` and raises
  `LedgerError("balance_drift")` otherwise (cannot happen through the services; guards direct DB edits).
- `simplify_debts(nets) -> list[tuple[int, int, int]]`: pure. Debtors (net < 0) and creditors (net > 0), each sorted by
  (−amount, member_id); repeatedly match the first of each, transfer `min(debt, credit)`, re-insert the remainder in sorted order.
  Each step zeroes at least one party, so ≤ n−1 transfers (≤ 2 for three, ≤ 3 for four). Input not summing to 0 raises `balance_drift`.
  Deterministic: ties break on lowest member_id.
- `record_settlement(group, from_member, to_member, amount_cents, date, notes="") -> Settlement`: checks amount > 0
  (`amount_not_positive`), members differ (`same_member`), both in `group` (`member_not_in_group`); currency = `group.currency`.
  One row, one `create` (atomic by itself); `twin` left null (006 sets it).
- `member_summary(group, member) -> {"paid", "owed_share", "net"}`: paid and owed over non-deleted expenses; net = paid − owed ± settlements
  (same as `net_balances()[member.id]`). A `personal` expense adds equally to paid and owed, so net is unchanged and `owed_share` grows.
  Member from another group → `member_not_in_group`.

## Tests

- `test_nets_sum_to_zero` — **KEY**: a mixed group (equal, exact, shares, personal, multi-payer, a settlement) sums to 0, and equals

- `test_full_settlement_zeroes_nets_partial_reduces_exactly` — 2500 settles to 0; 1000 leaves 1500.

- `test_simplify_is_deterministic_on_ties` — equal debts resolve by lowest member_id, same output on repeated calls.
- `test_edit_and_delete_change_nets` — `update_expense` amount change and `delete_expense` are reflected on next call (no stale cache).

## Edge cases (risky)
- Member with no activity → present with 0. Group with no members → `{}`; `simplify_debts({})` → `[]`.
- Debts that do not pair evenly (e.g. 100/−33/−33/−34) → 3 transfers, each exact, sums preserved.
- Overpaying settlement makes the payer's net positive; allowed (people do pay extra), nets still sum to 0.
- Soft-deleted expense with settlements against it: settlements remain, so nets can show the settlement as a credit; correct.
- Multi-payer expenses: paid sums per payer row, not only one payer.

## Production checks (expected numbers)
- A pays 5000 equal A/B → A +2500, B −2500; B settles 2500 → 0/0.
- 10.00 equal over A,B,C paid by A (1000 → 334/333/333): A +666, B −333, C −333; simplify → [(B,A,333),(C,A,333)].
- Nets {1: +100, 2: −33, 3: −33, 4: −34} → [(4,1,34),(2,1,33),(3,1,33)] (debtor tie 33/33 broken by id).
