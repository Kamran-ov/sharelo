## Proposal

### Layout (new Django app `importers`, added to `INSTALLED_APPS`; no models, no migration)
```
backend/importers/__init__.py, apps.py
backend/importers/splitwise/__init__.py
backend/importers/splitwise/client.py     # the only network code
backend/importers/splitwise/mapper.py     # pure: JSON -> mapped rows, no DB, no network
backend/importers/splitwise/importer.py   # service: orchestrates, the only DB writer (via ledger services)
backend/importers/management/commands/import_splitwise.py   # argument parsing + printing only
```

### `client.py`
- `SplitwiseClient(api_key: str)`; `from_env()` reads `SPLITWISE_API_KEY`; empty or unset →
  `LedgerError("missing_api_key")` (the command turns it into a non-zero exit). The app itself
  does not need the key to boot; only this command does.
- `_get(path, params) -> dict` — `urllib.request` GET to
  `https://secure.splitwise.com/api/v3.0/<path>` with `Authorization: Bearer <key>`, 30 s
  timeout, HTTP error → `LedgerError("splitwise_http", "<status> <path>")`. Body parsed with
  `json.loads(text, parse_float=str)` so no number ever becomes a float.
- `get_current_user()`, `get_group(group_id)` (`get_group/<id>`: name, members with
  `id/first_name/last_name/balance[]`), `get_categories()`, `get_expenses(group_id)` which pages
  `get_expenses?group_id=&limit=100&offset=` until a page shorter than 100 comes back and
  returns the concatenated list. (`get_groups` from the ticket is replaced by `get_group/<id>`:
  one group is all the command needs; listed under Plan notes.)

### `mapper.py` (pure functions, dataclasses out)
- `parse_cents(s: str) -> int`: regex `^\d+(\.\d{1,2})?$` on the string; `"12.5"` → 1250,
  `"0.10"` → 10, `"1000"` → 100000. Anything else (`"-1.00"`, `"33.333"`, `"1e3"`, `""`) →
  `LedgerError("splitwise_amount", ...)`. Integer arithmetic on the two string halves only.
- `CategoryMap.from_api(categories_json, our_categories)` → `{sw_category_id: our_category_id}`
  built by **(parent name, child name)**, because `Other` exists under six parents; Splitwise
  top-level ids map to their own name with no parent. Unknown id → `Uncategorized/General`,
  and the mapper reports it (`unknown_category` with the Splitwise name).
- `map_expense(raw, *, user_map, category_map, group_currency, rate_for) ->
  MappedExpense | MappedSettlement | Skipped`:
  1. `deleted_at` not null → `Skipped("deleted")`.
  2. `cost` → cents; `0` → `Skipped("zero_cost")`.
  3. Per user: `paid_share`/`owed_share` → cents; zero entries dropped; ids through `user_map`
     (unmapped never reaches here — see importer step 2).
  4. **Sum check per side** (payers vs cost, owed vs cost): equal → fine; off by exactly one
     cent → that cent is added to / taken from the **lowest member id with a non-zero share on
     that side**, logged (`logger.warning` with the Splitwise id) and reported as
     `cent_adjusted`; off by more → `LedgerError("splitwise_sum_mismatch", "<id>: <side>
     <sum> != <cost>")`.
  5. `payment: true` → exactly one payer and one receiver, distinct → `MappedSettlement(from=
     payer, to=receiver, amount)`; any other shape → `LedgerError("splitwise_payment_shape")`.
     Direction: Splitwise records "A paid B" as A `paid_share`, B `owed_share`; our settlement
     raises the sender's net, so `from_member = A`.
  6. Currency: `currency_code == group_currency` → amounts as is. Otherwise
     `rate = rate_for(date, currency_code)`, `amount = convert_with_rate(cost, rate)`, and both
     sides are rescaled with `split_shares(amount, cents_by_member)` (the one rounding rule,
     so both sides sum to `amount` exactly); `original_amount_cents = cost`,
     `original_currency`, `rate_used = rate`. A foreign payment is converted the same way and
     its `notes` keep `"Splitwise: 20.00 USD"` (Settlement has no original fields).
  7. `split_type` from the final group-currency cents: one ower who is the only payer →
     `personal`; one ower, one payer, different → `full_for_other`; owed equals
     `split_equal(amount, owers)` → `equal`; otherwise `exact`. (Read-side labelling only;
     balances use the stored cents, never the label.)
  8. `date` = Splitwise's `date` (an ISO UTC instant) converted to **Europe/Rome**, then its
     date part (`"2021-07-03T22:30:00Z"` → 2021-07-04; `"2021-01-03T12:00:00Z"` → 2021-01-03).
     Decided in plan review (Open questions 2). The mapper also reports, per row, whether the
     Rome date differs from the UTC date part (`date_shifted`), for the dry-run printout. `description[:300]`, `notes = details or ""`.
- `external_id = str(raw["id"])` on every mapped row.

### `importer.py` (service; rule 8)
`import_group(client, *, splitwise_group_id, group, user_map: dict[int, int], dry_run) ->
ImportResult` (counts, first 10 mapped rows, unknown category names, cent adjustments,
balance check):
1. Fetch group, categories, all expenses (network happens before any DB write).
2. **Validate the map before mapping anything**: every Splitwise user with a non-zero
   `paid_share` or `owed_share` in a non-deleted expense must be in `user_map` → otherwise
   `UnmappedUsers([(id, "First Last"), ...])` (names from the group members, falling back to
   the expense's user object for people who left the group). Map values must be distinct
   members of `group` → `LedgerError("member_not_in_group")` / `LedgerError("map_not_one_to_one")`.
3. Map every expense (pure). The mapper does **not** stop at the first problem: each row's
   `LedgerError` is collected as `(sw id, code, detail)` and mapping continues with the next
   row. `rate_for` = `rates.rate(date, cur, group.currency)`; a missing rate is a collected
   `no_rate` (Open questions 4), including a currency the ECB never publishes (e.g. `ARS`).
   If the list is non-empty, both the dry run and the real run print **every** error (one line
   `  <sw id>  <code>  <detail>`) and stop with exit 1, nothing written.
4. Existing ids: one query each on `Expense.all_objects` / `Settlement.all_objects` for
   `source="splitwise", external_id__in=ids` (all groups, soft-deleted included) →
   `Skipped("existing")`. **This lookup is what makes re-runs create nothing** (KEY).
   The same query returns each existing row's `group_id`. If any fetched id already exists in
   a group **other than** `--into`, the run (dry or real) prints
   `Already imported into another group: group <id>: <n> rows` per group and stops with
   exit 1, nothing written — a first run into the wrong group never turns into a silent
   `created 0` on the right one.
5. `dry_run` → return the result; no `ImportBatch`, no rows.
6. Otherwise one `transaction.atomic()`: create `ImportBatch(group, source="splitwise",
   label="splitwise group <id> <name>")`, then `create_expense(...)` /
   `record_settlement(...)` per mapped row with `source="splitwise"`, `external_id`,
   `import_batch`; finally `rows_seen = len(expenses fetched)`, `rows_created`,
   `rows_skipped`, `finished_at`. Any error rolls back the batch and every row.
   Invariant asserted: `rows_seen == rows_created + rows_skipped`.
7. Balance check (report only, real run): Splitwise's member `balance` is a list with one
   entry per currency, so the check is per currency:
   - **Group-currency line, exact:** for each mapped member, our net computed from the DB over
     this group's `source="splitwise"` rows whose external id is a Splitwise expense in the
     group currency (expense payers/splits and settlements alike; foreign rows excluded) vs
     Splitwise's entry for the group currency. Printed `EUR  <name>  splitwise +X  ours +X`,
     with ✗ on any difference. Restricting to these rows makes it exact even if the group
     holds manual rows too.
   - **Each foreign currency, one labelled line per member, never compared:**
     `USD  <name>  Splitwise +X USD; ours +Y EUR at ECB rates, not compared`, where Y is our
     net over the imported rows of that original currency.
   (`balance_check(group, splitwise_group, ids_by_currency)` is a function in `importer.py`,
   so the test calls it directly.)
8. Dry run also prints `Dates shifted by Europe/Rome: <n>` and the first 20 shifted ids with
   both dates, so the impact of rule 8 is seen before writing.

### `ledger` change (additive)
`record_settlement(..., source=Source.MANUAL, external_id=None, import_batch=None)`; the
unique violation `uniq_settlement_source_external_id` → `LedgerError("duplicate_external_id")`
(same savepoint pattern as `create_expense`). Existing callers unchanged.

### Command
`python manage.py import_splitwise --group <sw_group_id> --into <our_group_id>
--map "<sw_user_id>=<member_id>" [--map ...] [--dry-run]`
- Malformed `--map` / unknown `--into` → `CommandError` (exit 1).
- `UnmappedUsers` → prints `Unmapped Splitwise users:` then one `  <id>  <name>` line each,
  plus our group's members (`<member_id>  <display_name>`) to copy into `--map`; exit 1.
- Success prints: `seen / created expenses / created settlements / skipped existing /
  skipped deleted / skipped zero cost / unknown categories (names) / cent adjustments (ids)`,
  the first 10 mapped rows (`date  description  amount  split_type  payers → owers`) on a
  dry run, and the balance check.

## Edge cases
- Users who left the Splitwise group still appear in old expenses: they need a `--map` too;
  names come from the expense's user object.
- A page of exactly 100 rows: the client asks once more and stops on the empty page.
- Splitwise rounding gaps of one cent (e.g. 1000.00 / 3) are corrected by our rule, never
  silently; gaps above one cent stop the run with the expense id.
- The same Splitwise expense already imported into a different group of ours: the run stops
  with exit 1 and lists that group's id and row count, nothing written (tested).
- Two runs at the same time: the second hits the unique constraint, its whole transaction
  rolls back; a re-run then skips everything already there.
- Foreign rows on a date older than the stored rates: listed as `no_rate` with every other
  error, nothing written; fix with `fetch_rates --since <first expense date>`.
- A currency the ECB never publishes (e.g. `ARS`): listed as `no_rate` and refused like any
  other error; `fetch_rates` cannot fix it. The remedy (manual rates) is an open point in
  `docs/PLAN.md` and out of scope here.
- `repayments` and Splitwise's `net_balance` are derived fields and are ignored for writing
  (used only in the balance check test).

Every mapping choice is frozen by the first real run (re-runs skip by id, nothing is
hard-deleted), so:
0. `pg_dump` the database before the real run, and import into a **new, empty** group. The
   only undo is restoring that dump (README says so).
1. `fetch_rates --since <oldest Splitwise expense date>` first, if any expense is not EUR.
2. `--dry-run` twice: `seen` (the client's fetched row count, payments and deleted included)
   is identical on both runs; `created expenses + created settlements + skipped == seen`;
   errors 0; unknown categories listed (expected 0 for a Splitwise-seeded tree); the Rome
   date-shift count is read and accepted.
3. Real run: the balance check's **EUR line has no ✗** for any member; foreign lines are
   labelled "not compared". `ImportBatch` latest row: `rows_seen == rows_created + rows_skipped`.
4. Second real run: `created 0`, `skipped == seen`, balances unchanged.
