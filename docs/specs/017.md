## Proposal

### Model and migration (`ledger`)
- `Member.guest_claimed_at = DateTimeField(null=True, blank=True)`.
  State, derived, never stored separately: **joined** = `profile_id` not null; **guest** =
  `profile_id` null and `guest_claimed_at` not null; **unclaimed** = both null.
  `Member.claim_state` property returns `"joined" | "guest" | "unclaimed"`.
- Migration `0009_member_guest_claimed_at`: add the field (schema), then a data step
  `UPDATE member SET guest_claimed_at = now() WHERE profile_id IS NULL` (RunPython,
  reverse no-op). Reason: every profile-less member that exists today was created by a guest
  session (or lost its profile via `SET_NULL`); without this they would all turn claimable from
  the link the moment we deploy, i.e. anyone with the link could take over an existing guest.
  No committed migration is edited.

### Services (`ledger/services/groups.py`, rule 8)
1. `add_placeholder_member(group, display_name, by_member) -> Member` — `by_member` must belong
   to `group` (`not_a_member` otherwise; the API guarantees it, the service still checks).
   Name stripped, 1–100 chars (`invalid_display_name`), `name_taken` via `_new_member`. Creates
   `profile=None, guest_claimed_at=None`.
2. `claim_member(token, member_id, guest_member_ids, profile=None) -> Member`, `@transaction.atomic`:
   - unknown token → `unknown_group` (404 at the API, as today's `not_found`); member not in
     that group → `not_found`.
   - with `profile`: `profile_already_in_group` if the profile has a member there;
     without: `already_in_group` if any id in `guest_member_ids` is a member of this group
     (one session = one person per group).
   - The claim is ONE guarded write: `Member.objects.filter(pk=id, group=group,
     profile__isnull=True, guest_claimed_at__isnull=True).update(...)`, setting `profile` or
     `guest_claimed_at=now()`. Zero rows updated → `member_already_claimed`. The `WHERE` re-check
     under Postgres' row lock is what makes two simultaneous claims leave exactly one winner; no
     read-then-write window. A profile claim that races into `uniq_member_group_profile` →
     `IntegrityError` mapped to `profile_already_in_group`.
   - with `profile`: `_auto_link(profile, group)` (006 rule, unchanged).
   - Returns the member; the caller (view) adds the id to the session for a guest claim.
3. `join_group_by_token(...)` without profile now sets `guest_claimed_at=now()` on the new
   member (an "I'm new" guest is claimed by its own session from birth).
4. `release_guest(member) -> None`: if `profile_id is None`, set `guest_claimed_at=None`;
   a member that has a profile is never touched (logout of a signed-in user must not free a
   joined member).
5. `adopt_guest_members(profile, member_ids) -> AdoptResult(attached, kept, refused)`,
   `@transaction.atomic`, one savepoint per member: for each id that is still a guest member
   (`profile_id is None`): if the profile already has a member in that group → `refused`
   `(member_id, "profile_already_in_group")` and the id stays in `kept`; else guarded update
   `profile=profile` where `profile__isnull=True` (an `IntegrityError` race → refused the same
   way), then `_auto_link`. Ids whose member already has a profile (any) or no longer exists are
   dropped from the session. The member row, its id and every payer/split row stay as they
   are; only `profile` changes.

### API
- `POST groups/{id}/members/ {display_name}` (`GroupScopedView`: any member, profile or guest)
  → 201 member row `{id, display_name, profile_id, is_guest, status}`; `name_taken`,
  `invalid_display_name` → 400.
- `GET groups/{id}/` member rows gain `status: "joined" | "guest" | "unclaimed"` (additive;
  `is_guest` unchanged: still `profile_id is null`).
- `GET join/{token}/` gains `unclaimed_members: [{id, display_name}]` ordered by id
  (`member_names` kept).
- `POST join/{token}/claim {member_id}` → `{group_id, member_id}` (same shape as join). Profile
  session → claim with profile; otherwise guest claim and `add_guest_member`. Errors: 400
  `member_already_claimed`, `profile_already_in_group`, `already_in_group`; 404 `not_found`
  (unknown token, member of another group). CSRF exactly as `POST join/{token}/`.
  Path without trailing slash as in the ticket, like the other action endpoints (`link`,
  `move-to-home`, `pause`).
- `sign_in` (register, login, Google): after `login()`, `adopt_guest_members(profile, ids)`;
  session `GUEST_KEY` = `kept`. Response = `me_body` plus `guest_refused:
  [{member_id, group_id, code}]` (always present; `[]` on `GET /me`).
- `LogoutView`: before `logout()`, `release_guest` every member id in the session's
  `GUEST_KEY` (guest and signed-in sessions alike).
- `make schema` regenerates `frontend/src/api/schema.json` / `types.ts`.

## Edge cases
- Two browsers tap the same name at the same moment → one guarded UPDATE wins; the other gets
  `member_already_claimed` and a refreshed list.
- Existing guest members at deploy → marked claimed by the migration, never exposed.
- Guest who joined "I'm new" and later the creator adds a placeholder with the same name →
  `name_taken` (unique constraint unchanged).
- Signed-in user taps a name while already in the group → `profile_already_in_group`.
- Guest session holding Janet logs in to a profile already in that group → sign-in succeeds,
  Janet stays a guest held by this session, `guest_refused` explains it.
- Session expires or cookies cleared without logout → `guest_claimed_at` stays set; the name is
  not claimable (see Open questions).
- A member id in the session that meanwhile got a profile (cookie copied to another browser that
  registered) → dropped from the session on next sign-in, never re-assigned.
- Balances, splits and analytics never read `guest_claimed_at`; claiming changes no money row.

## Production checks (expected numbers)
- Before migrate: `n = Member.objects.filter(profile__isnull=True).count()`. After:
  `Member.objects.filter(profile__isnull=True, guest_claimed_at__isnull=False).count() == n` and
  `Member.objects.filter(profile__isnull=True, guest_claimed_at__isnull=True).count() == 0`.
- `GET join/{token}/` for every existing group returns `unclaimed_members == []` right after deploy.
- Sum of nets per group unchanged by the migration (no money rows touched): run
  `net_balances` for every group before and after, diff = 0 for every member.

## Open questions
- Assumed: a member added by name is claimable by anyone with the link (ticket decision C);
  no PIN or approval step.
- Assumed: a guest session holds at most one member per group (`already_in_group`), same as the
  existing join returning the existing member.
- Assumed: attaching a guest member at sign-in does not make that group the profile's main
  group; the 006 link rule applies as in a normal join.
- Assumed: sign-in reports refusals in the response (`guest_refused`) instead of failing the
  sign-in, since the ticket says the guest membership is kept.
- Assumed: logout of a signed-in user also releases guest members still held by its session
  (the refused ones), since the session that held them is gone.
- Follow-up suggestion (not built): a guest name whose session expired without logout stays
  taken for ever; a later ticket could let group members "free" a guest name.
