## Proposal
Thin DRF views. Serializers validate types only. Every rule stays in the services; nothing new in `ledger/services/` except small, pure helpers named below. New package `backend/ledger/api/{urls,views,serializers,presets}.py`, routed under `/api/` next to the accounts routes.

**Access (the one rule everything shares)**
- `ledger/api/access.py`: `group_for(request, group_id) -> (Group, Member)` loads the group (404 `not_found` when missing, `LedgerError("not_found")`) and calls `require_member`. A missing group and a non-member get the identical 404 body. **Every** view under `groups/{id}/` begins with this single call, via a `GroupScopedView` base class whose `initial()` does it and stores `self.group`, `self.me`; no view reimplements it.
- Detail lookups (`expenses/{eid}`, `recurring/{rid}`) filter by `group=self.group` so an id from another group is 404.
- Guests: `require_profile(request)` → 401 `not_authenticated` for create-group, link, move-to-home. Everything else works for a member of either kind. Guest join needs a CSRF-protected anonymous POST: join views derive from `CsrfProtectedAPIView`; the other POST/PATCH/DELETE views use `SessionAuthentication`, which only enforces CSRF for authenticated users, so group views also derive from `CsrfProtectedAPIView` (a guest session is anonymous to DRF). All write routes therefore enforce CSRF.

**Routes** (`/api/`, no trailing-slash surprises: paths as in the ticket, with trailing slash)
- `groups/` GET (profile memberships ∪ guest memberships, newest first) and POST `{name, currency, as_main?}`. `as_main` omitted → true iff the profile has no main group. Calls `create_group`. Currency validated as 3 uppercase letters by the serializer; a service rejection is passed through.
- `groups/{id}/` GET: `{id, name, currency, share_token, members: [{id, display_name, is_guest}], my_member_id, is_main, link_active}`. `is_main` = `profile.main_group_id == id`; `link_active` = the profile's `GroupLink.active`, `null` for main group or guests. `share_token` is returned so members can invite others.
- `groups/{id}/link` POST `{active}` → `set_link_active`; `no_link` (main group) → 400.
- `join/{token}/` GET public `{group_name, currency, member_names}`; unknown token → 404 `not_found`. POST `{display_name}` → `join_group_by_token(token, name, profile)`; anonymous → `add_guest_member`; a repeated guest join with the same name in the same session returns the existing session member (the service raises `name_taken`; the view checks `member_for` first and returns it, so the same guest joining twice yields the same member). Another visitor reusing a taken name still gets 400 `name_taken`. Signed-in callers join with their profile.
- `categories/` GET tree `[{id, name, children: [{id, name}]}]`, one query pair, no auth needed.
- `groups/{id}/category-defaults/` GET `{category_id: {preset, params}}` for set rows; PUT replaces the set (validated through `split_for_preset` with a dummy total of 100 over the group's member ids, so a bad preset is refused at save, not at the next expense).
- `groups/{id}/expenses/` GET: `from`, `to` (dates), `category` (matches the id or its children), `member` (payer or split member), `page` (50 per page, `{count, page, results}`; ordering `-date, -id`), `prefetch_related` payers/splits, no per-row queries. POST: body from the ticket.
- `groups/{id}/expenses/{eid}/` PATCH, DELETE (soft, `delete_expense`; repeated delete is 204).
- `groups/{id}/balances/` GET `{currency, nets: {member_id: cents}, transfers: [{from, to, amount_cents}], members: [{member_id, paid, owed_share, net}]}` from `net_balances`, `simplify_debts`, `member_summary`.
- `groups/{id}/settlements/` GET (newest first) and POST `{from_member, to_member, amount_cents, date, notes?}` → `record_settlement`; member ids resolved inside the group (an id from another group → 400 `member_not_in_group` from the service, never a 500).
- `groups/{id}/move-to-home` POST `{to_profile, amount_cents, date}` → `move_debt_to_home(group, my_profile, to_profile, …)`. Group is the main group → 400 `not_a_sub_group` (new code; the service's existing `trip_is_main_group` is renamed in the view mapping layer, not in the service, because 006's tests pin it. Ticket text wins on the public name; the mapping is one dict, tested). Non-main groups of a caller with no main group → service's `no_main_group`.
- `groups/{id}/recurring/` GET, POST; `recurring/{rid}/` PATCH, DELETE; `recurring/{rid}/pause|resume|skip` POST. `resume_rule` and schedule edits receive `today = datetime.date.today()` from one `today()` function in the view module that tests monkeypatch.
- `GET /api/schema/`, `/api/docs/` via `drf-spectacular`. Add `drf-spectacular>=0.27,<1` to `requirements.txt` (only new dependency). `Makefile` target `schema` runs `manage.py spectacular --file ../frontend/src/api/schema.json --validate --fail-on-warn`; `lint` additionally runs `schema` into a temp path and diffs it against the committed file (CI fails when stale). Views get `@extend_schema` where inference is not enough so there are zero warnings. Schema served at `/api/schema/` is public (no secrets in it).

**Preset mapping (`ledger/api/presets.py`, pure)**
`to_service_preset(preset, params, my_member_id, member_ids) -> (split_type, params)`:
- `half`: the two-member 50/50 → `equal` over exactly the two members; with ≠ 2 members → 400 `invalid_params` ("half needs exactly two members"). It is the API name for `equal`, and stored `split_type` is `equal`.
- `personal`, `equal`, `exact`, `shares`: passed through (params as the service documents them).
- `full_for_other`: params optional; `other_id` filled by the service for two-member groups.
- `percentage`: API param `{percent_payer}` (integer 0–100, two-member groups) → `basis_points {payer: p*100, other: (100-p)*100}`; or `{basis_points: {...}}` passed through for advanced use. Any non-integer `percent_payer` → 400 `invalid_params` (no float, no Decimal; JSON numbers like `50.5` are refused, basis points are the finer route).
- Unknown preset → service `unknown_preset`.
The mapping lives in `ledger/api/` because it renames API vocabulary only; the splitting arithmetic stays in `splits.py`.

**Expense body → service**
- `payer_member` must belong to the group (service `_validate` checks; view passes ids unchanged).
- With `preset`: `create_expense_from_preset(group, preset=…, payer_id=…, params=…, description, currency=group.currency, date, category, amount_cents?, original_*?, rate_used?)`. Omitted `preset` → `default_split_for(group, category)`, then the same path. Foreign: `original_amount_cents` + `original_currency` (+ optional `rate_used` override, which the service already checks against the stored rate) and no `amount_cents` → converted amount and `rate_used` come from `resolve_foreign_amount` inside the service.
- With `payers`+`splits`+`split_type` (advanced): `create_expense` directly. `preset` and `payers` together → 400 `invalid_request`.
- PATCH: loads the expense (group-scoped, non-deleted), merges the body over current values, and calls `update_expense`. When only descriptive fields change (description, date, category, notes), the existing payers/splits are re-sent unchanged. When `amount_cents`/`preset`/`payer_member`/`params` change, splits are recomputed through the same preset path; the response is the full expense.
- Response shape: `{id, description, amount_cents, currency, original_amount_cents, original_currency, rate_used (string or null), date, category, split_type, source, notes, payers: [{member, paid_cents}], splits: [{member, owed_cents}], created_at}`. `rate_used` as a string, never a JSON float.

**Errors**: `accounts.api.errors.handler` is reused unchanged: every ledger code is 400, `not_found` is 404. `not_a_sub_group` (400) is the only new public code.

## Edge cases (risky)
- Outsider vs. missing group: identical status and body (no existence leak). Covered by the KEY test.
- Guest session id for group X must not open group Y (covered by `member_for` tests from 009 and an extra row: guest of `rome` gets 404 on `home`).
- Signed-in user with a profile member **and** a guest id in one group: profile member wins (009). The API's `my_member_id` reports it.
- Pagination: page past the end → 404 `not_found` (DRF default), page 0 or non-integer → 400 `invalid_request`.
- Dates are ISO `YYYY-MM-DD`; `from > to` → empty list, not an error.
- PATCH of a deleted expense → 404 (default manager hides it).
- Amounts: JSON booleans or floats for `amount_cents` → 400 `invalid_request` from the serializer (`IntegerField` with a strict check), so `50.0` and `true` never reach the service.
- Foreign body with `amount_cents` **and** `original_*` set inconsistently → the service's `rate_mismatch` (400).
- Two concurrent PATCHes: the last write wins; `update_expense` is one transaction so the rows are never mixed. Stated, not solved.
